# Continuation State

## Responsibility

This document is the compact, replace-in-place description of OuttaMyWay's **current engineering continuation boundary**: the active concern, the accepted understanding needed to continue it, the unresolved question, and the next bounded engineering step.

It is **not** a repository-status dashboard.

Git owns the exact accepted `main` commit and repository chronology. The executable version owners own current TEST build identity. GitHub Issues and pull requests own their own open/closed state and discussion history. Canonical-release identity is owned by release governance. This document must not duplicate those authorities merely for convenience.

> **Continuation Boundary != Repository Status Dashboard**

### Maintenance contract

Only the copy on accepted `main` is authoritative.

On a working branch, this file describes the continuation state that would become current **if that branch were accepted and merged**. The branch copy is therefore a proposed replacement, not an assertion that the branch itself is accepted.

Update this file only when an Engineering Increment materially changes at least one of:

- the active engineering concern;
- the accepted understanding required to continue that concern;
- the unresolved boundary or question; or
- the immediate next bounded engineering step.

Do **not** touch this file merely because another pull request merged, a commit SHA changed, a TEST build number advanced, an Issue changed status, or unrelated repository work moved forward.

In particular, this file must not maintain:

- an exact `main` SHA;
- a mirrored current TEST build identity;
- a repeated canonical-release identity;
- a branch/PR validation-status ledger;
- an exhaustive list of open Issues; or
- completed engineering chronology.

Those facts are either generated by the merge event itself or already have stronger authoritative owners.

> **Merge-Address Paradox** — a document accepted by a merge cannot truthfully pre-record the exact commit identity created by that same merge.

A useful Continuation State should remain correct across unrelated merges. Its review question is:

> **Could a new engineer determine what is currently being worked on, what has already been established for that work, what remains unresolved, and what bounded question comes next?**

### Prospective-selection ownership

The peer-family tranche confirms that one tightly coupled processing chain can remain several semantic authorities rather than collapsing into a planner subsystem.

Candidate Support owns the complete supported prospective universe and exact-picture provenance.

> **Candidate Enumeration != Preselection**

> **Support Projection != New Operational Picture**

> **Portfolio Composition != Decision**

Constraint Evaluation owns complete independent mandatory admissibility verdicts.

> **Constraint Verdict != Preference**

Decision owns compatibility, preference, deterministic tie-break where legitimate, and explicit selection or non-selection among supported admissible alternatives.

> **Decision Selection != Responsibility Establishment**

> **Decision May Select Governing Scope; It May Not Rewrite Support.**

> **Non-Selection Is a Decision Outcome, Not Missing Decision.**

The chain therefore remains:

### Discovered conformance question — Issue #170

Applying the Decision contract exposed a current Architecture-to-source/test conformance question.

Accepted Architecture places mandatory Constraint Evaluation before Decision and defines Decision as selecting among supported, constraint-admissible alternatives.

Current source first identifies globally mandatory-PASS Candidates, but `ProspectivePortfolioDecisionPolicy` selects a support group using Candidate-inventory/support metadata rather than the verdict set. `DecisionSelector` then filters admissible Candidates to that chosen group. Existing structural tests deliberately preserve `lowerPrecedenceConstraintFallback=false`.

This yields the named boundary:

> **Support Precedence != Admissibility Bypass**

A preferred support group's existence does not, by Decision preference alone, grant authority to suppress an otherwise supported Candidate that passed every mandatory Constraint. If a stronger exclusion relationship is intended, that relationship must be explicitly discovered and owned by Architecture rather than inferred from source ordering.

Issue #170 owns the unresolved investigation. The current hypotheses are:

1. implementation/test drift — group compatibility is applied too early; or
2. a missing architectural concept — some existing precedence is actually a stronger semantic exclusion relationship.

No implementation change is justified until that distinction is tested. The Specification records the accepted architectural contract and treats the current source ordering as a conformance question, not authority.

Issue #170 does not by itself block continued Specification migration. If its investigation disproves current Architecture, the affected Architecture and Decision Specification must be revised before implementation is defended.
